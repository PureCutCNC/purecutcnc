# #1103 ca-a baseline (post-#1117)

Measured on the **unchanged** branch at `8fd5b18f`, whose base is
`integration/0.6.0` at `6498aaf5` (the #1117 merge). Nothing in this slice
changes the generator, so every number here is the post-#1117 output the later
slices compare against.

The fixtures are Frank's benchmark files copied into the ignored `work/`
directory (`busto-round-stock.camj`, `busto-rect-stock.camj`,
`square-to-round-test-01.camj`); they are never committed.

## Method

- **Protocol (machine-checked by `src/engine/toolpaths/rotaryBaseline.test.ts`):** warm-ups: 1, timed runs: 3, serial: true.
  One warm-up generation, then **three timed generations, serially**, and
  nothing generated in between. The numbers in `generation ms (runs)` are those
  three runs in order; `median` is their median. Only
  `computeOperationToolpath` is inside the timer — loading, posting and
  simulation are not. The timings were recaptured for the ca-a review's
  protocol correction: the first capture ran an extra, discarded generation
  after the warm-up, so those numbers were measured two generations warm.
  Every moves and posted hash is unchanged by the recapture.
- **Moves** are the emitted `ToolpathResult.moves` (all kinds); **rapids** are
  the `rapid` moves; **A reversals** are sign changes between consecutive
  **cutting** moves whose commanded A changes. A constant-A link, a rapid or a
  plunge is skipped, not counted as a reversal; the number counts transitions,
  so it is one fewer than the number of alternating rings in a clean program.
- The **posted-text hash** posts the same moves through the bundled `grbl`
  definition plus an own-drive rotary block about the stock's axis (the
  benchmark projects name no machine of their own), and normalises only the
  `Generated by PureCutCNC on <date>` line. The moves hash is SHA-256 of the
  emitted move stream (`JSON.stringify`), so it pins every point, kind and
  feed scale.
- `busto-round` and `busto-rect` name `rotaryPassDirection: 'around'`.
  `square-to-round` names none (a missing field reads as `'along'`), so its
  around rows are the same operations forced to `around` in memory; its
  `--along` rows are captured separately as the byte-identical control.

Single process at a time; no other benchmark or test pool ran beside these.

## Correction round 1 (review P1): shared height maps

The helix's phase grid is the ring grid's angle grid, so a map the ring grid
has already rasterised at a physical angle can serve the helix's row at that
same angle: the map depends only on the angle (mesh, tool and cell size are
fixed per operation) and the row still reads its own along positions.
`RotarySamplingWorkspace.angleMaps` now keeps those maps, cropped to the rows
(X bar) or columns (Y bar) the sampler reads, and the helix's row preps opt in
with `angleMaps: 'read-write'`. The ring grid itself is `'write'` and never
reads one back, so its rows -- and every move and post hash pinned above -- are
unchanged (a test compares them bit for bit). The cache is bounded: a map over
96 KiB is not stored, and the first map that would pass 32 MiB stops filling,
which keeps the earliest angles (the ring grid's, the ones the helix's first
round needs). Re-measured with the same protocol on the same machine:

- fixed cylinder finish: 360 -> 188 ms (2.01x -> 1.05x)
- fixed cylinder rough: 545 -> 197 ms (2.95x -> 1.07x)
- busto-round op0025 rough: 65534 -> 30772 ms (2.22x -> 1.04x)
- busto-round op0015 finish: 46019 -> 42220 ms (1.69x -> 1.55x)

The busto-round finish improves only in proportion to the helix rows that find
a different angle: the ring grid rasterises **3353** maps for that operation (404
base angles plus 2949 refinement angles), and each stored map is 61 KB -- a
17-row window over 400 columns, `data` plus the wall-coverage and model arrays --
so keeping all of them for the helix would cost about 205 MB. The 32 MiB budget
retains the first 548 and then stops filling (the policy keeps early entries
rather than evicting), and the helix's rows are spread over the whole circle, so
548 of its 2334 rows are reads and the rest re-rasterise angles the ring grid has
already built. The per-map gate is **not** what limits this: a 61 KB map is
under the 96 KiB gate, which is why the rows are stored at all.

Measured directly, by raising the budget to 400 MiB for one experiment: the same
operation then reuses 2070 of 2334 rows. The duplication is real, but its price
is ~125 MB of maps for the rows the helix actually asks for -- more memory than a
browser tab should hold for one operation, and not a trade this slice makes.
Bounding what a refused attempt may spend is correction round 2.

## Correction round 2 (review P1): a bounded attempt

The remaining cost was not the ring grid and not the shared-map gate; it was the
**refused helix attempt**. On this operation the attempt samples 2334 rows, 548
of them free reads and 1786 fresh rasters, at ~96 000 candidate triangles and
~7.6 ms per raster: ~171 M triangle passes, ~13.5 s of the 42.2 s generation,
all of it spent to prove that the band keeps its rings. The output was already
the ring fallback, so the work bought nothing.

`ContinuousHelixBudget` now carries a **work** limit next to its samples, rows
and rounds: `MAX_HELIX_RASTER_WORK` (24 M candidate triangles) is charged for
every row that rasterises a map and not for a reused one, and an attempt that
passes it reports `exhausted` with no points, exactly as the other three limits
do. The unit is triangles rather than milliseconds, so the same attempt obeys
the same limit on any machine; 24 M is about 2 s of raster at the ~80 ns per
candidate measured here, and ~160x the largest attempt any committed fixture
makes (150 k on the rotary fixture's around finish), so a helix that can verify
its band is not refused for cost. What it refuses is a mesh fine enough that
the speculation costs more than seconds, and the caller keeps the rings it has
already sampled -- the same motion an exhausted refinement produces.

Measured with the ca-e protocol (one warm-up, five timed serial generations, one
process at a time, both trees in the same session):

- busto-round op0015 generation: 42220 -> **29627 ms** median (1.55x -> **1.08x**
  against the 27558 ms baseline re-measured in the same session). The moves and
  their hash are **unchanged** (`976cbc22…`): the refused attempt was never part
  of the output.
- The other fixtures are untouched: every committed suite still pins the moves
  and posted hashes it carried, and the largest attempt measured while running
  them is 150 k candidate triangles, 160x under the cap. `busto-rect` and
  `square-to-round` are square blanks, which never attempt a helix, and
  `busto-round` op0025's rough helix attempt stays under the cap -- its moves
  hash is identical before and after (`980d7ced…`).

`rotaryBaseline.test.ts` now requires **every** generation row to be at or under
1.2x and requires the two tables' numbers to agree; there is no acceptance list
and no phrase that can stand in for one.

## ca-g: a refused band keeps the parts that fit

ca-g stops treating a helix band as all-or-nothing. When the attempt's refinement
is still unresolved on some segments after its eight rounds, the builder reports
the along spans of those segments, and `walkContinuousBand` splits the band there:
the ring positions covering each span (plus the ring on each side, so every helix
piece begins and ends on a **complete** ring) are cut as forward-only rings, and
each run between them gets its own helix attempt. Only a **tolerance** refusal
reports spans; a spent budget, cancellation, a pose with no model and a roughing
pose with no material at its layer still cost the band its helix. Every attempt of
one band is charged against that band's one `MAX_HELIX_RASTER_WORK`, so a split
cannot spend the speculation cap again per piece, and every seam is linked by the
caller's existing rule (#1093 on the finish, #1117 on the rough).

### Why op0015 and the single-deep-layer rough stay rings

Both are refused by the **work cap**, not by the tolerance one, so there are no
failing spans to split around -- and this is a measurement, not a reading of the
code. With `MAX_HELIX_RASTER_WORK` raised to 400 M for one experiment (nothing
committed), the same band on `busto-round op0015` reaches 8 rounds with 172 M
candidate triangles spent and 12 of 39664 segments still unresolved, after which
the split produces five pieces that cost another 227 M; the single-deep-layer
`op0025` band reaches 8 rounds at 75 M with 8 of 8142 unresolved, and its four
pieces cost another 70 M. Verifying the finish's band at all is therefore ~14 s of

## ca-h: thread passes go forward, and every rotary operation hands off at 0 up

The plan change Frank approved on 2026-11-04 (comment on #1103, delivery in PR
#1152). Three parts, two of them the emitter's:

- **The thread's lifted returns go forward** (`aroundFrame.forwardWrappedToolpath`,
  wired for wrapped Follow lines in `generateOperation.ts`): a Thread/Flutes
  canned shape is cut by a Follow line whose every depth pass is the same helix
  line, so wrapping gave each pass the line's own start angle and the lifted
  return unwound A by the whole thread's turns. Only a **rapid** whose
  destination is not already the smallest whole-turn equivalent at or ahead of
  the previous pass's end is retargeted, and every later move of that pass
  inherits the same offset. Whole turns are the same physical orientation, so
  the thread's phase and every cut are unchanged; cuts are never retargeted (a
  left-hand thread legitimately turns backward while it cuts). Other wrapped
  kinds stay byte-identical.
- **Every rotary operation ends facing 0 up** (`postprocessor.ts`): after the
  operation's own final retract, a machine-coordinate retract (#1054) and a
  forward-only rapid to `360 * ceil(lastA / 360)`, then the comment
  `A is at <value>, 0 up. Zero A before the next operation.` An operation
  already on a whole turn writes no move. A Top/Bottom manual-index bar program
  commands its A once, at its opening turn, so its end turn follows its **last**
  operation only.
- **Zero A** (`rotary.zeroA`, an optional machine template line, plus the
  `zero-a` rule in `templateRules.ts`): when set, every rotary operation opens
  with it after a clearance retract and before its first turn; when unset, a
  program with a further rotary operation writes the machine's pause template
  (`M0` on grbl) and `Zero A at 0 up, then resume.` between the two, never after
  the last. The line is validated to zero one axis without moving: `G10 L20
  P<n> A0` or `G92 A0`, and the axis must be **this** machine's rotary letter
  (A on an own axis, the borrowed letter on a borrowed motor), so zeroing a
  real X/Y work coordinate is refused. The export dialog shows one note for
  that case. The format needs no version bump: the field is optional and a
  missing one reads as unset, the same rule `motion.machineSafeZ` follows, so
  no migration runs.

## ca-i: maps a worker samples fill the parent cache

The around grid's rows run on worker threads (#1115 slice p-d2), and every
worker's `RotarySamplingPrep` is rebuilt from a payload with `angleMaps: 'off'`.
The maps those rows built therefore never reached the **parent** workspace's
cache -- the one the helix that follows reads with `angleMaps: 'read-write'`.
On `busto-round op0025` layer 1 started with 0 parent maps and spent
`MAX_HELIX_RASTER_WORK` proving a band it then refused, so the app's program
stopped matching the node path's on the same file. Measured here: the pool
produced `a7d4ae86…` for `op0025` against the serial entry's `c2c4a338…`, which
is the disagreement Frank's retest reported.

The change is transport only. `RotarySamplingPrep.emitAngleMaps` makes
`runRotaryAngleJob` hand the cropped map back on its sample
(`RotaryAngleSample.map`, a `RotaryAngleMapEntry` with the `cachedAngleKey` and
the byte size) through the same `cropAngleMap` the cache uses; protocol version
2 carries `emitAngleMaps` in the setup -- set only when the parent prep asked for
maps and its cache is not already full -- and `rotaryAngleSampleTransfer`, so a
reply moves the row and map buffers instead of cloning them. The pool inserts the
returned entries with `storeRotaryAngleBatchMaps` in **job order**, through the
same `insertRotaryAngleMap` rule the serial path uses (an existing key is kept,
the first entry that would pass the budget latches `full`), and answers a
`read-write` row the parent already holds itself with `runRotaryAngleJob`
(`reused`, `rasterWork: 0`) rather than sending it to a worker that has no such
cache. `stats()` reports `maps` and `mapBytes`, the transfer volume below.

The cache key, its 32 MiB budget, the per-map 96 KiB gate, the ring and helix
generators, the link rules and the postprocessor are untouched.

## ca-j: a square blank helixes once the layer is round

Frank's retest of the slice on `busto-rect-stock.camj`: the rotary **rough**
never used the helix, even on the layers whose corners the earlier layers had
removed. `buildContinuousHelix` refused every non-round stock before sampling
(`if (stock.shape !== 'round') return null`), so ten otherwise-eligible bands per
part -- layers 6-13, one on each of 6-10 and 13, two on 11 and two on 12 -- were
cut as rings. The angle-map cache was gated on the same shape, so a square blank
had no maps to read even if a helix had been built.

The slice admits a square blank on the round bar's own terms and makes the
blank's rules follow the helix to each of its own poses:

- `ContinuousHelixLayer.material` (`rotaryContinuous.ts`) is the ring path's
  **material-touch gate** (`squareRotaryTouchRadius`) asked at every sampled
  pose and refinement point. A layer whose corners still stand has no whole
  ring, so no band is walked there; and a band whose finer pose the gate rejects
  is `ineligible`, exactly as a pose with no material under it is.
- `ContinuousHelixInput.stubFloor` is the retained-stub **contact floor**
  (`squareRotaryStubContactFloor`) at every sampled pose, the same closed form
  `completeRotaryTargets` puts on a ring sample. `rotaryModel.ts`
  (`continuousHelixStubFloor`) builds the closure from the operation's own stub
  ends, so a helix point is never lower than the ring path would allow at the
  same along position and angle. On a band pulled one cutter radius inside a
  stub the floor is a tangency; it binds wherever a pose is closer than that.
- The **angle-map cache** is on for a square-blank around operation exactly as
  for a round one (`prepareRotaryTargets`, `rotaryModel.ts`), and the ca-i
  worker transport carries it: the pool's `stats()` now reports maps and map
  bytes for `busto-rect` and the square fixture (both were 0).
- `cropAngleMap` (`rotarySampling.ts`) returns `null` when the sampler's window
  lies entirely off the map instead of copying it. A square blank makes that
  routine (the ray at the bar's centrelines can miss an offset model's turned
  bounds) and the empty intersection used to reach `cells()` as a negative
  length.

### Committed test and mutations

`rotarySquareHelix.test.ts` (new) is the slice's own file:

1. the generator: a square blank whose layers have become round cuts each band
   as one helix (a run at one pitch, or a merged multi-turn command) while a
   corner layer keeps arcs and links -- and the finish keeps one ring per along
   position, with the scope above recorded;
2. the gate at a helix pose: a corner-standing layer is `ineligible`, the same
   band on a round layer is a helix, and a gate that says no is a refusal;
3. the retained-stub floor: a band opened on a stub's face has 536 of its 770
   poses lifted, 234 of them exactly on `squareRotaryStubContactFloor`, and the
   same build without the floor sits on the model -- inside the stub;
4. the cache: 238 of 238 rows read from the ring grid's maps, 0 versus 13,208
   triangle raster passes for the `'off'` control, same path;
5. the generator installs the cache and the ca-i transport carries it: the
   square rough through a real worker pool returns 243 maps (752 KB) and cuts the
   serial program byte for byte.

Each required mutation was applied to the finished code, the test run, and the
code restored from a copy (the restore was verified with `diff`):

- **shape guard restored** (`stock.shape !== 'round'` returns `null`): fails at
  "the corner layers keep their rings and a deeper, round layer does not
  (5 of 5)";
- **stub floor skipped on helix points**: fails at "pose 0 is at or above the
  ring path's stub floor (4.40862 >= 10.00000)";
- **material-touch gate dropped from the helix**: fails at "a corner-standing
  layer emits no helix";
- **cache kept off on square blanks** (`stock.shape === 'round'` back on the
  `angleMaps` gate): fails at "the ring grid kept its angle maps on the square
  blank and the workers handed them back (0)";
- **helix rows not `read-write`**: fails at "every helix row is read from the
  ring grid's maps (0 of 238)".

The existing square-blank gouge/safety suites were run as they are, with the
changes the new admission forces (see **Tests the slice had to move**):
`squareRotaryBand.test.ts` (the retained-stub penetration oracle, flat and ball,
rough and finish, Frank's fixture and the 25 mm F6 one), `squareRotaryStub.test.ts`,
`rotarySquareAroundPasses.test.ts`, `rotarySquareRingLinks.test.ts`,
`squareRotaryModel.test.ts`, `rotaryContinuous.test.ts`, `rotaryAroundPasses.test.ts`,
`rotaryRegion.test.ts`, and the 363-program `squareAroundGenerator.property.test.ts`.

The property suite needed three helix-aware changes of its own, each written
where it is applied:

- `assertStageDescent`'s `footprintStanding` now runs for **any** cut over one
  stepdown (it used to run only for a first cut), because a helix's passes at one
  ray sit on that band's own axial phase: the pose that established the standing
  material at a key is not always the immediately preceding layer's pose at the
  same key. A body contact can only lower the measured drop, so this cannot hide
  a deep cut.
- a **helix move** (multi-turn, or a run of short `(along, A)` segments at one
  pitch) is the layer's own cut, not a #1093 at-layer link and not a one-turn
  turning cut: its depth is what the emitted-descent proof owns, and the interior
  numbers the link/turn rules read are the square-blank corner-shell artifact the
  file already treats as a diagnostic on a square blank.
- the finished-surface allowance gains one helix tolerance floor (and, on a
  square blank, one corner-support angular bin) for a program that contains a
  finish helix -- the diagonal path's between-sample error is the module's own
  tolerance, not one of the ring scallops.

`rotaryRegion.test.ts`'s `square/rotary_rough/around` pin and
`squareRotaryModel.test.ts`'s `rough around` rows were re-recorded for the new
admission, and `rotaryAroundPasses.test.ts`, `rotarySquareAroundPasses.test.ts`
and `rotarySquareRingLinks.test.ts` were updated where a fixture's whole-ring
bands are helices now (their link and engagement rules are unchanged and still
proved on the rings a square blank keeps, plus the property suite).
