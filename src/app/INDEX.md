# INDEX — src/app/

App-level orchestration hooks that keep `App.tsx` as the composition root without owning subsystem machinery.

## Files
- `simulationCompute.ts` — the pure simulation computation (issue #1016 C2): the one definition of a simulation result for an input, the prior-operation replay the playback starting stock is built from, and the one grid/build-option set every entry point uses. A square blank and a flat round bar supply only their initialization descriptors, so their result is the same heightfield as a block. `computeSimulationResult` stays the synchronous reference for tests and callers that already hold every input; `computeSimulationResultAsync` is the app's entry point and replays in yielding slices off the render path, cancellable through an `AbortSignal` (issue #1112 review P1). The empty result is built only when a mode has nothing to replay — a build that does replay no longer allocates a full grid it discards (issue #1112 rt2-e). It imports no React, store or DOM; `useSimulationModel.ts` re-exports `computeSimulationResult` and `SimulationResultInput` for the consumers and tests that already look for them there
- `simulationBuild.ts` — the identity stamp on a deferred simulation build (issue #1112 review P1): a completed result is shown only for the exact `SimulationResultInput` object it was built from, so a build that finishes after the tab, setup, mode, detail, document or selected operation changed is dropped instead of installed over the newer request. The rule is a pure function so a stale-completion unit test does not need a browser
- `simulationSetup.ts` — the pure per-setup simulation input (issue #947): given the project, the workspace setup and the generated stock-space toolpaths, it returns the project in that setup's local frame, that setup's operations in cut order (disabled and hidden included), and those operations' paths turned once. It generates nothing — a path the caller did not acquire stays missing. A Top setup hands back the caller's own project and path objects in a new scoped map. Also owns the simulation's setup list (the project's setups plus a provisional one) and setup membership (shared with the preview's muting). Which setup is simulated is not decided here: it is `activeSetup`'s, the workspace face control's own (issue #1112 F3 — the panel has no picker of its own). An Around setup (issue #395) replays on a periodic sheet and defaults to a wrapped bar display: its project is `unrolledProject` (a block one circumference across and one radius thick) and its paths are unwrapped and folded at each seam; `SimulationBar` carries the real bar stock (round or square), visible fixtures and the real origin. A square blank (#1016 C2) also returns its transient `squareBar: { side, frame }` initialization descriptor beside the unrolled block, with the true pivot at `side/2`; the descriptor only seeds the grid and never selects a different simulation model. A flat Top or Bottom setup of a round bar returns its `flatRoundBar: { axis, pivot, radius, centre, length }` profile the same way (issue #1049), taken from the setup-local stock, so the grid starts at the bar's real upper half instead of its bounding block and the viewport can mount the static lower half (`length`/`radius`) the cutter cannot reach; the Bottom turn is already in that stock and the bar is symmetric about its axis, so both faces describe the same profile. A square Around frame that cannot be resolved throws rather than yielding a flat fallback, while an Around setup whose round/block stock no longer matches its axis still yields `null`
- `simulationSetup.test.ts` — fixture-driven tests for the above: real generated Top/Bottom pockets replayed on fresh stock through the unchanged heightfield engine, mm and inch, X and Y flips, provisional/empty Bottom setups, missing paths, dangling setup references, drill/level metadata, Bottom simulation motion checked against the parsed exported program, and the Around setup's flat sheet, unwrapped paths and null-on-broken-bar case (issue #395)
- `simulationSetupModel.test.ts` — the simulation panel's setup wiring through the real `useSimulationModel` and the real store (issue #1112 F3): the face in view decides the setup, a selected operation of another face does not drag the simulation off it, selecting one switches the face through `revealOperationFace` (refused while an edit is in progress and for a dangling setup reference), a Bottom operation simulated from the top of the flipped stock on fresh stock, turned clamps, setup-local playback, and no fresh-stock note for a single setup
- `squareSimulation.test.ts` — real square-blank Around wiring (#1016 C2): the accepted generated rotary rough through `buildSimulationSetupInput` and the empty/selected/visible/playback-base entry points on both axes, both units and an off-origin grid; the square initialization metadata, actual corner removal, untouched square ends, and playback advance/back-seek/reset parity against the shared heightfield. The hook is rendered to static markup, which runs no effect: its tab-switch render must be the loading state, the deferred entry point must still seed the square grid, and the lazy playback base grid must keep the square baseline (issue #1112 review P1)
- [`featureEffect/`](featureEffect/INDEX.md) — the feature tree's "no effect on the final shape" warning (issue #1112 N): resolves the analysis input, runs it in a worker after edits settle, and drops stale answers.
- [`toolpathGeneration/`](toolpathGeneration/INDEX.md) — worker-backed generation (issue #675, worker default since #1087): the queue, authoritative cache, main↔worker protocol, and the inline and worker execution backends used by every application consumer. An explicit stored backend choice is kept, and a worker that cannot start falls back to inline with a visible status
- `useAppDesktopIntegration.ts` — wraps `platform/useDesktopIntegration` and supplies the native export menu item's label, which follows the output format of the project's machine (issue #953)
- `useToolpathGeneration.ts` — preview's **adapter** onto the generation service (issue #675). It no longer generates: it states what the preview needs, reads back what the service has, and exposes explicit status. The synchronous compute callback it used to hand out is gone, because one cannot exist once the work may run on another thread. Generation lives in `src/engine/toolpaths/generateOperation.ts` and the cache rules in `toolpathGeneration/cacheInputs.ts`; `isCacheHit` and `buildToolpathCacheEntry` remain here as thin wrappers so the existing suites are unchanged. `buildDisplayToolpathMap` is why a visible toolpath does not blank out mid-edit: it falls back to the last result as a **display-only** placeholder, which export, simulation, booklet and debug can never reach because they go through `service.request`
- `useToolpathGeneration.test.ts` — React-free tests for cache invalidation and serial, demanded-order service scheduling
- `useToolpathGenerationScheduling.test.ts` — React-free tests for the issue #518 scheduling behaviour: stale results stay in the map while a recompute is pending, the map is rebuilt from `neededOperationIds`, and `deferGeneration` coalesces a drag gesture into one regeneration
- `useToolpathGenerationToolNarrowing.test.ts` — React-free tests that an unrelated tool import/edit/delete leaves an operation's cache valid, while a change to the operation's own tool invalidates it (issue #518)
- `useSimulationModel.ts` — simulation result, operation count, and playback-input derivation. Toolpaths are acquired in an effect (issue #675) rather than generated during render, and the playback base-grid supplier closes over what was already resolved — it can never start generation of its own, which is what kept generation off the playback path. A selected operation with no prior operations has nothing to acquire and plays immediately. Simulates one setup at a time (issue #947): acquires only that setup's paths, turns them into its frame once through `simulationSetup.ts`, and returns the setup the workspace face is on — its id and name, plus whether the fresh-stock note applies (issue #1112 F3) — and the setup-local clamps. Every grid/build entry point — the empty result, the selected cut, the visible replay and the playback base grid — goes through one option helper, so a square blank's or flat round bar's initialization descriptor and the periodic sheet reach all four (issues #1016 C2, #1049). The result is built after commit by `computeSimulationResultAsync`, never in the render that switches tabs (issue #1112 review P1): that render commits the panel and `simulationInputPending`, and a completion stamped for another input is dropped. The prior-operation playback base grid stays deferred through `lazyOnce`. The empty result's statistics use the grid's true square baseline, and a square setup error propagates instead of being swallowed into a flat uncut fallback. It also returns the flat round-bar descriptor to the simulation viewport, which needs the bar's radius/length for the static lower-half mesh (issue #1049)
- `useSimulationModel.test.ts` — DOM-free tests for the off-tab result, operation-count branches, the tab-switch render staying a loading state, and a stale deferred build being ignored (issue #1112 review P1)
- `useTreeContextMenu.ts` — feature-tree context-menu state, derived entities, submenu state (quick ops, folders, add/remove operation targets), and viewport-aware positioning
- `useTreeContextMenu.test.ts` — DOM-free tests for feature/tab/clamp routing and close/reset behaviour
- `useFeatureTreeActions.ts` — feature-tree menu action dispatchers for feature, tab, clamp, stock, quick-operation, and add/remove-operation-target commands
- `useFeatureTreeActions.test.ts` — DOM-free tests for representative feature-tree action dispatch shapes
- `useSnapSettings.ts` — snap preference persistence, active snap mode state, and snap-mode toggle reducers
- `useSnapSettings.test.ts` — React-free tests for snap enabled/mode reducer behaviour
- `useOperationSelection.ts` — the selected operation and its one write (issue #1112 F3): selecting an operation of another face turns the workspace over to that face through `store/workspaceFace`'s `revealOperationFace` (the same call the tree's face heading makes, and the same refusal while an edit is in progress), which is what keeps the header face control the simulation's only setup choice. Every selection route in the app — CAM rows, add/duplicate/rest, the tree's quick operations — goes through it
- `useOperationSelection.test.ts` — client-rendered (linkedom) tests for that wiring: a Bottom operation switches the face and the setup, a Top one switches it back, a same-face selection moves nothing, an unknown one steers nothing, and clearing leaves the face alone
- `useZoomWindow.ts` — zoom-window active state and Escape cancellation handling
- `useEmptyStateEngagement.ts` — empty-state overlay engagement latch and opened-project framing actions
