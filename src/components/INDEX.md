# INDEX — src/components/

React UI. Components are organized by feature area. Plain CSS for styling — no UI libraries.

## Top-level files
- `AppErrorBoundary.tsx` — top-level React error boundary
- `ErrorScreen.tsx` — fatal-error fallback UI
- `Icon.tsx` — `<Icon id="..." />` renders an SVG sprite reference (`icons.svg#id`)
- `IconGallery.tsx` — dev/debug grid of all available icons
- `Select.tsx` — shared styled `<select>` wrapper; an option may carry a `group` heading (consecutive options sharing one render a single non-interactive label), which the project machine picker uses for "Other machines" (issue #1028)
- `ToolpathVisibilityPanel.tsx` — toggles for showing/hiding toolpath layers
- `ToolpathLevelRail.tsx` / `toolpathLevels.ts` / `useToolpathLevelSelection.ts` — transient, display-only level selection for planar multi-level operations; shared by the 2D and 3D previews while surface and waterline paths fail closed to the complete view
- `ToolpathGpuSuggestion.tsx` — non-blocking GPU tip for a stored Canvas choice, outside the toggle row; `canvas/toolpathGpuSuggestion.ts` detects repeated slow navigation draws, and `canvas/useToolpathGpuSuggestion.ts` owns browser-local dismissal and result-scoped suggestion state.
- `plasmaKerfPreview.ts` — the display-only plasma kerf model (issue #961): the torch's kerf width in project units and the identity-cached split of a toolpath's moves into contour, lead and pierce geometry. Nothing here generates, stores or exports, and it is covered by `plasmaKerfPreview.test.ts`.
- `toolpathSetupMuting.ts` — which operations' toolpaths the 2D and 3D previews draw muted: those cut in a setup the workspace is not on (issue #947), by the same membership rule as the simulation and export; nothing for a single-setup project
- `toolpathVisibility.ts` — `ToolpathVisibility` type, default visibility constants, and the cached feed-colour legend steps (issue #535) (kept out of the panel component for fast refresh)
- `UnsupportedMobileScreen.tsx` — phone-sized-device blocker screen shown instead of the app (extracted from `main.tsx`)
- `errorFormat.ts` — shared error formatting
- `useIconIds.ts` — hook listing available icon IDs

## Subfolders (by area)
- `common/` — shared cross-panel UI primitives. `DisclosureSection` is the reusable collapsible "Advanced" section (progressive disclosure); its open/collapsed state persists via the pure helpers in `common/disclosureState.ts`.
- `canvas/PlasmaStartPointPicker.tsx` / `canvas/plasmaStartPoint.ts` — plasma contour click/tap capture with compact draggable shared edit controls, attached per-contour markers and targeted closed-contour projection, covered by `canvas/plasmaStartPoint.test.ts`; transient pick intent lives in `cam/plasmaStartPointPick.ts`.
- `canvas/plasmaKerfBand.ts` — the 2D sketch's plasma kerf preview (issue #961): a translucent one-kerf band under the centre line, contour segments under `cuts` and lead segments under `leadIns`, plus fixed-size pierce markers under `plunges`; pure view code, covered by `canvas/plasmaKerfBand.test.ts`.
- `canvas/` — 2D sketch canvas: drawing, snapping, panning/zoom, pointer handling, creation workflow panels, and overlap disambiguation through `useOverlapFeaturePicker` / `OverlapFeaturePicker`. `CanvasWorkflowAction` and `canvasShortcuts.ts` keep every canvas-panel action’s accessible label, visual shortcut hint, and keyboard binding aligned; `EditSketchPanel` owns the active sketch-edit session’s controls and confirmation handoff. `FeatureDistributionPanel` / `useFeatureDistributionWorkflow` provide the one-shot grid/radial/path copy workflow (issue #205), with canvas preview driven by `sketch/featureDistribution.ts`. `TextLayoutPanel` / `useTextLayoutWorkflow` lay an **already placed** text run on a circle or along a guide (issue #671) — a post-create edit reached from the same arrange group as distribution, not part of the text tool; `canvas/textLayoutPreview.ts` draws what Apply would produce, and preview and commit share `sketch/textPlacement.ts` so they cannot drift apart. `previewPrimitives.ts` keeps Line/Construction geometry stroke-only; `previewPrimitives.test.ts` covers that rendering-role policy. `stlTopViewRenderer.ts` maps imported-model top-view images through their full instance transform, covered by `stlTopViewRenderer.test.ts`. Dimension annotations + tape measure render via `canvas/dimensionRendering.ts` (pure geometry in `sketch/dimensions.ts`); `canvas/operationSnapshot.ts` renders static operation booklet images; `drawOperationSnapshot` is the context-agnostic drawing half, and since issue #924 it draws the toolpath through the same display merge as the live canvas rather than stroking every emitted move (`operationSnapshot.test.ts`). `canvas/toolpathDisplay.ts` owns the display-only scaled-world toolpath cache: it coalesces same-style strokes up to three canvas pixels of accumulated travel and indexes lines, collisions, source markers, and arrows so panning queries only the canvas viewport without changing emitted motion. `canvas/navigationActivity.ts` and `canvas/useNavigationViewState.ts` defer direction-arrow calculation/drawing while navigating, restoring detail after pointer release or 150 ms wheel idle without changing visibility settings. `canvas/toolpathDisplayFixture.test.ts` measures geometric error against the original rectangle and 882,899-move raster workloads. `canvas/toolpathArrows.ts` owns the 2D direction-arrow placement pass, cached per `(toolpath, scale, visibility)` and stored in scaled-world space so panning only shifts it by the view offset and still hits — that pass was 93.7 ms per animation frame on #664's 249,663-move fixture against 26.7 ms to draw the 9,899 arrows it selects. `toolpathArrows.test.ts` pins the rules and then pins the port itself against the pre-#664 algorithm transcribed as an oracle, on the real fixture.
- `viewport3d/` — Three.js 3D preview of the CSG-derived model, including toolpath overlay helpers, shared camera orbit controls (`orbitControls.ts`), view-preset data (`viewPresets.ts`, whose isometric view looks up from below while the workspace is on Bottom, #947), and the single-button view dropdown (`ViewPresetMenu.tsx`) used by both the 3D and simulation viewports. `toolpathOverlay.ts` owns the **shared** toolpath layer set — which move kinds each layer draws and, for rapids, which half of the Z split (`zFilter`) it claims — consumed by both this viewport and the 2D canvas so the two views cannot disagree about layer membership (issue #482). It also owns `toolpathLayerBuckets`, the identity-cached one-pass version of that split both renderers use on the render path — the per-layer filter it replaced was five full copies of the move array per animation frame (issue #664). It owns the wrapped Around display too (issue #395): `stockSpaceToolpath` maps a path whose points carry the rotary angle `a` onto the bar with `stockSpacePoint`, subdividing each turning move into pieces of at most 5° so the curve follows the bar, while an angle-free path is handed back as the very same object and moves array. `arrowBatch.ts` draws every direction arrow of one colour as two objects (a `LineSegments` of shafts plus an `InstancedMesh` of heads) instead of a `THREE.ArrowHelper` each; on #664's 249,663-move fixture that was 29,741 scene objects and 19,835 draw calls per frame, which the viewport's render loop re-submitted for the life of the session. Its geometry reproduces `ArrowHelper` exactly and `arrowBatch.test.ts` asserts that against a real `ArrowHelper` rather than against recorded numbers. `webglRenderer.ts`, `webglContextGuard.ts` and `WebglStatusOverlay.tsx` are the WebGL failure handling both 3D views share: renderer creation returns `null` instead of throwing when the browser denies a WebGL2 context, so a GPU-less browser still opens the 2D workspace rather than the error screen (issue #786); the guard forwards context loss and restore; the overlay explains either state with each view's own messages.
- `viewport3d/plasmaKerfObjects.ts` — the plasma kerf band and pierce markers for the 3D preview and the Simulation tab (issue #961): a `worldUnits` `LineSegments2` band one kerf wide at the top of the sheet plus a fixed-size `THREE.Points` marker ring, with its own disposal; covered by `viewport3d/plasmaKerfObjects.test.ts`.
- `simulation/` — heightfield simulation viewport and playback controls; `aroundView.ts` owns the Around bar pivot, frozen-sign turn and vertical tool pose, plus the frame-value key (`aroundFrameKey`/`sameAroundFrame`) the viewport's Around effects depend on instead of the rebuilt frame object's identity (issue #395 G3), all tested by `engine/simulation/aroundWrap.test.ts`; the key also carries the bar's shape and thickness so a square blank and a round bar of the same box, or a resized blank, never reuse a stale preview (issue #1016 C2-R2V). It also owns the bar readout (`barReadout`: the wrapped tool point in the real project origin plus the program's unreduced `a`), covered by `simulation/aroundView.test.ts`. An Around setup is drawn as the cut bar turning under the tool, with no separate flat view (issue #395 G3). `SimulationViewport` draws a round bar and a square blank through one heightfield path — `createHeightfieldTexture`/`createHeightfieldMaterial`, the instanced surface strips and `createInstancedBoundaryGroup` — and takes its bounds and framing from the grid's radial envelope (`grid.stockTopZ`, the corner radius on a square blank) about the true pivot, so taller corners are not clipped. Playback uploads only the controller's dirty rectangle with `uploadHeightfieldRegion` and falls back to `updateHeightfieldTexture`; static and playback results report removal against each cell's own starting height when the grid carries `initialTopZ`.
- `cam/` — CAM panels (tools, operations, parameters); per-parameter reference icons via `OperationParameterReference`. `CAMPlanDialog` is the two-column CAM Plan review/apply surface; `CAMPlanOperationEditor` edits transient recommendations and reads `operationFields.ts` applicability so operation-specific controls stay aligned with the normal editor, while shared tabs have one separate setup row. `ToolLibraryDialog` renders the focused library-import modal, listing only the machine mode's own tool family (#960); the pure filtering/selection helpers live in `toolLibraryDialogModel.ts` with their own structural tests. `operationTargetLists.ts` computes the context menu's "Add/Remove to operation" candidates against the store's own `isOperationTargetValid` guard. `SurfaceSlopeFields.tsx` provides the optional min/max CL-surface slope controls for 3D finish operations. `operationFields.ts` declares the operation panel's field order and grouping as data — one ordered table of `{ id, group, paramRef, appliesTo }` that `CAMPanel` walks — so a control's position is a property of the field rather than of the JSX branch it was written into (#559). Which patterns the `pattern` dropdown offers is no longer the renderer's own list: both it and `operationFields.ts`'s applicability read `engine/toolpaths/pocketPatterns.ts`, the same table the generators dispatch on, so a kind can never be offered a pattern its generator does not implement (#609). `OperationAddMenu` partitions the Add menu on the same validity hint the rows already carried: kinds the selection can take render first, the rest collapse into one counted `DisclosureSection`, and an empty selection states its single precondition once instead of eleven times (#732).
- `cam/machineMode.ts` — the machine mode the CAM panel follows (issues #960, #1028): `machineMode` derives `router` or `plasma` from the **project type** — a plasma project is `plasma`, milling and rotary are `router` — and `operationOffer`, `operationCutOnMachine`, `uncutOperationCount`, `selectableToolTypes`, `libraryEntryOffered`, `showsFaceSwitch` and `showsMillingAuthoring` decide what that mode may add — restricting new offers while an existing operation or tool of the other family stays selectable as what it already is, and offering the plasma cut in a milling or rotary project as `needs-plasma-project`, a **project-type** reason rather than a machine one (issue #1034); `machineMode.test.ts` pins every rule in both modes. The CAM panel's Add menu and tool type list, the tool library and the workspace face switch all read it (#960); the Auto plan button and the Add-tab control are router-only.
- `nesting/` — sheet nesting UI (issue #741): the Nest panel, its pure form state, and the Web Worker that runs the packer. See [nesting/INDEX.md](nesting/INDEX.md)
- Top / Bottom / Around faces (issues #945, #395, #1112): `layout/FaceSwitch.tsx` is the workspace's one compact face control (in the workspace header on desktop, in the sketch's face row on tablet shells) — it names the face in view ("Bottom · flipped X") and opens a menu of the project's faces and the "Show other side" ghost overlay, replacing the old segmented pills, flip chip and eye; the menu's rules live in `layout/faceSwitchMenu.ts` and the flip in its label in `layout/faceSwitchExtras.ts`. It is hidden entirely by a plasma project type (#960, #1028) unless the project already uses both faces, and `layout/FaceBanner.tsx` is the tablet-only row above the sketch that carries it (desktop has no row). The tree's face section headings are the second home of the same switch action and the same refusal while an edit is in progress (#1107): they carry no Active/Ghost badge, and the face being worked on says "Nothing here yet" until something is drawn there. On a round bar in a rotary project the menu gains an **Around** entry (the `face-around` icon, `appShell.face.around*`), always enabled — a missing, non-rotary or wrong-axis machine cannot withhold it, and machine suitability is enforced at the output boundary instead (issue #1034) — and the entry is absent entirely in a project whose type is not rotary (issue #1028); an Around setup is not a flip, so its features get their own tree layer and `AROUND` chip, ordinary Top-style Z properties with no change-face entry (and the change-face entry is hidden while the workspace is on Around too, #1015 slice K), their own CAM section (a one-line card header named after the Around setup, no cross-face picker, reach check or Move… on rotary passes; issue #1102) and export program, and Print/design-SVG export is disabled while Around is active. `canvas/viewTransform.ts` mirrors the 2D view for a Bottom setup from the #944 transform (`computeSketchViewTransform`, `worldArcToCanvas`); `canvas/faceOverlay.ts` draws the other face's features as dashed ghosts and the marker for where the Top origin lands; `canvas/aroundSheet.ts` reports the sheet's clamp bands, turn lines and a band per visible imported model at its extent along the bar, which `canvas/scenePrimitives.ts` draws under the sheet's features and toolpaths (issue #1015 slice K) — and since #1016 C2-U1V a square blank is a bar here too, unrolling through `engine/aroundFrame.ts`'s nominal reference cylinder (radius = side / 2, circumference = π · side, never the physical perimeter): `canvas/aroundToolpaths.ts` and the operation snapshot unwrap a square blank's rotary rough/finish path through that same frame, `canvas/scenePrimitives.ts` gives it the round bar's turning centreline (`barCentreline`, at the true box pivot) while its cross dimension stays the side and never takes the Ø, and the 3D overlay turns it about that same pivot. Whether an Around operation may be *authored* on a square blank is still the active-face / operation-validity guard's decision — square production dispatch and authoring guards are a separate slice; the toolbar offers a square blank the one-shot **Square to round** solid instead of the round-only Thread/Flutes entries and 2D drawing controls (#1016 C2-U2); `canvas/faceView.test.ts` covers the oriented view for both flip axes and ghosts staying out of ordinary hit-testing and snapping, plus canonical construction reference picks on both axes (#994). `canvas/referencePickIntent.ts` classifies the existing point/profile/segment reference phases and supplies shared live-state reads; constraints and edit subjects stay face-local. Foreign construction guide rows route armed distribution/text pickers directly without edit selection. In `feature-tree/`, `FeatureTree` groups machining features into Top face / Bottom face layers once the project uses both, `FaceZRange` gives a Bottom feature the same Z range slider Top uses, read with the stock flipped (a 0.25-deep Bottom pocket in 0.75 stock reads 0.75 → 0.5) and written back through `spanFromFaceDepth`, with the stored stock Z span read-only beneath it, `feature-tree/faceZRangeEdit.ts` plans that control's stock-space writes (a pure function with its own test: one side per edit, an inside-out entry refused, a Line moved from Top put back on the bottom face), `FaceChip` holds the face tag and the authoring-face properties row, and `ChangeFaceDialog` is the confirmation every authoring-face change goes through. The project row's **Project type** (issue #1028) sits under Name and Units: it is chosen once, in the New project dialog, and shown as read-only text afterwards (issue #1046, so there is no type-change dialog or store action any more); `projectTypeChoice.ts` owns the pure decisions (the type label keys and the machine picker's grouping of the machines that suit the type before the rest under "Other machines"), and the machine note under the picker says when the selected machine does not suit the type. Typed and displayed angles are face-local: `canvas/manualEntry.ts` takes the `FaceAngles` maps as a required argument for the length-and-angle inputs (line, slot, polygon, gear) and the typed rotation, the radial Sweep field, the backdrop Angle and the imported-model Rotate X/Y/Z fields convert at the field, the rotate preview label on the canvas reads the turn as seen (`measurements.ts`), a grid distribution's X/Y spacing converts the same way through `faceOffsets`, and `canvas/faceAngles.test.ts` fails if a conversion is dropped or applied twice. Text-on-arc angles are in the run's own frame and need none. A Top-only project renders none of it but the switch.
- `feature-tree/` — sketch feature tree UI (reordering, visibility, grouping) plus `PropertiesPanel`, `projectTypeChoice.ts` (the Project type UI's pure decisions, #1028), `ZRangeSlider` (generalized single/bulk Z-range with locked handles), `BulkTabProperties`/`BulkClampProperties` (bulk-edit panels with center-preserving dims and mixed-value display), `DraftTextInput`/`DraftNumberInput` (shared inline-edit fields), `mixedValue.ts` (pure common/mixed aggregation helpers), the extracted feature/tab/clamp context menu, and `ModelOrientationSection` (post-import 3D orientation + lift controls for imported models). Its stock panel offers the project type's shapes and, for a **square blank** (#1016 C2-U2), swaps Diameter for Side and resizes through `resizeSquareStock` + `originAfterStockEdit` so the side is the physical thickness, the pivot is side / 2 and a manual origin survives.
- `layout/` — app shell (toolbars, sidebars, mode switching), including the shared `AppearanceControl` and `LanguageControl` (interface-language selector backed by `src/i18n/`), and `CommandNoticeToast.tsx` — the transient visible reason for a refusal with no control to hover (issue #1112 A2); toolbar internals are documented in `layout/toolbar/INDEX.md`. The toolbar's Around group carries the C1 Thread/Flutes entries on a round bar and the one-shot Polygon / hex and Square to round entries (#1016 C2-U2), which follow the stock shape and unmount with the face.
- `cam/generationGearState.ts` — pure rules for the generation gear: when it is flagged, and which renderer notice shows (issue #1102)
- `cam/GenerationSettingsMenu.tsx` — generation status, Stop/Resume/Retry and, in the sketch, the GPU / Canvas toolpath display with its fallback and Retry (issue #1102; the execution-backend choice was removed there: generation always uses the worker when one exists), behind the gear in the CAM panel header (issue #675). Started in the status bar and moved here: this is where generation is visible, with the generating operations listed directly below. All of it sits behind one gear rather than split across two surfaces — a backend picker in the panel and a Stop button in the status bar would be two homes for one concern. Because a menu hides its contents, the gear marks itself when generation is paused or failed, and carries the status in its accessible name so a screen reader gets it without opening anything. Stop is **disabled** under the main-thread backend rather than offered and quietly ineffective, and says why
- `cam/toolpathToggle.ts` — the one eye in the operations toolbar that shows or hides every toolpath (issue #1102): it hides while any toolpath is drawn
- `cam/OperationNoteField.tsx` — an operation's description: "+ Add note" until there is one, then the textarea (issue #1102)

- `project/` — project-level UI (new/open/save, stock, machine, units), including `newProjectProjectType.ts` (the New project dialog's project type tiles and their arrow-key order, issue #1102), `newProjectStock.ts` (the New project dialog's blank template stock, issue #1046: a block for milling and plasma, and the bar a rotary project's own fields describe — round or square, diameter or side, length, axis — with no block intermediate), `UnitConversionDialog` and `UnitConversionContext` for the shared explicit convert-vs-reinterpret units decision. ## Conventions
- `cam/bookletExport.ts` — the operation booklet export as named stages (issue #924): preparing the toolpath, drawing the snapshot, building the PDF, choosing where to save. Each stage is announced before it starts and the two that hold the main thread wait for a paint first, so `CAMPanel`'s stage text and the booklet button's spinner describe the step actually running. `bookletExport.test.ts` pins the order.
- `cam/ScallopHeightField.tsx` — Constant scallop's single finish-quality input, with units, strict positive-height validation, and a display-only legacy stepover conversion that preserves saved output until edited.
- GPU sketch renderer, default since 0.6.0 (issue #1087; #683): `canvas/gpuToolpathRenderer.ts` retains full XY buffers and composites per-layer coverage masks; `gpuToolpathShaders.ts` owns screen-space shaders. `gpuToolpathAnnotations.ts` reuses Canvas arrow/debug rules in an operation-ordered texture. `useSketchToolpathRenderer.ts` owns lazy loading, cancellation, disposal and fallback/retry; `toolpathRendererPreference.ts` owns the application-local codec, the `gpu` default and the non-persisting DEV comparison override (covered by its test). `toolpathWebglSupport.ts` owns the one strict WebGL2 request (refusing software rasterisers), the DEV-only software-WebGL test switch and the suggestion probe, so the app never advertises a GPU that would fall back. `renderSketchToolpaths.ts` selects GPU or Canvas fallback without changing navigation ownership. Both backends draw a mirrored Bottom view from the same stock-space buffers (the GPU through a per-axis view map) and paint another setup's toolpaths muted, beneath the active setup's (#947). `toolpathStyles.ts` shares styles with Canvas/booklet output. A stored Canvas choice is kept and a runtime without hardware-accelerated WebGL2 (missing, or software-only on SwiftShader) falls back to Canvas visibly; booklet snapshots always use Canvas. See [`tools/gpu-toolpath-poc/`](../../tools/gpu-toolpath-poc/INDEX.md) for the comparison harness and device gates.
- Heavy compute (CSG, toolpath gen, sim) is debounced. See `Viewport3D` (150–300ms typical).
- Mutations go through `projectStore` actions only — never mutate Zustand state directly from components.
- For touch/tablet styling see `src/styles/tablet.css` and [`planning/TABLET_UX_DESIGN.md`](../../planning/TABLET_UX_DESIGN.md).

- `cam/PlasmaOperationFields.tsx` — plasma-only kerf side, swirl reversal, line/arc leads and optional contour-start XY; milling controls are excluded by the field policy.
- `cam/setupSections.ts`, `CamSetupSectionView.tsx` — CAM groups by saved or provisional active setup, program numbers, registration status and scoped export (#946). `SetupPropertiesDialog.tsx` / `SetupRegistrationEditor.tsx` edit flip axis, name, shared-origin display, references and notes; setup deletion lists operations before confirmation. `SetupOperationControls.tsx` confirms validated Move and measures stock-Z reach; `CrossFaceTargetPicker.tsx` explicitly targets opposite-face through subtracts/models without selecting sketch ghosts; `RotaryTargetPicker.tsx` is the rotary operation's target checklist over the project's imported models (issue #1015 slice K), written through `rotaryTargetToggle` in `operationValidity.ts` so the last ticked model cannot be removed and a region filter riding on the target survives; since #1096 the panel also renders the standard "Use current selection" row for a rotary operation, so a selected closed Around region joins the target as a mask (an update route requires a non-empty selection so a stray click cannot reset the target); the same module's rotary operation and add-menu hints admit either bar shape, round or square, so a generated square-to-round model is a valid target with no spurious round-stock message while a block still reports it (#1016 C2-U1). `SetupDialogShell.tsx` supplies focus, Escape and scroll handling. An Around section in a project whose type is not rotary carries `CamSetupSectionView`'s note — the operations are kept but not cut (issue #1028).

- `cam/rotaryOperations.test.ts` — Rotary rough/finish authoring contract: Around model-only targets, defaults, support cache/units/file persistence and exact field policy (#1015 slice D).
