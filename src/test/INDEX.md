# INDEX — src/test/

Shared test-only infrastructure.

## Files

- `cpuRatio.ts` — ratio-based CPU-work measurement helper for stable performance assertions; use it with an invariant-work reference rather than an absolute timing budget
- `spreadLimit.ts` — `maxSpreadableLength()`, the largest array this engine can spread into a call, measured by search rather than hard-coded (issue #668). Tests that must exceed the argument limit assert against the measured value, so a fixture that quietly stopped exceeding it fails instead of passing while proving nothing
- `guitarTopFixture.ts` — the 332 × 470 mm procedural carved guitar-top mesh used for #697’s strategy measurements and #702’s 0–30° slope-filter acceptance; it is retained as a synthetic test model rather than represented as a sourced CAD model
- `surfaceSlopeFixtures.ts` — closed analytic height-field meshes and normalized finish projects for deterministic slope-domain tests
- `waterlineHillsFixture.ts` — the rolling-hills-with-flats model #698 is calibrated against, generated rather than checked in as an STL so the shape is readable and the resolution is a parameter. It mixes the four surface characters a 3D finish has to handle at once — a large flat background, flat plateau tops on clamped domes, steep dome flanks, and a gentle ramp — because waterline is uneven across them by construction. `finishSurfaceWaterlineBudget.test.ts` runs a coarse mesh four times; `scripts/waterline-coverage-probe.ts` runs a fine one whose facets do not show up in the measurement
- `waterlineMesaFixture.ts` — a flat background plane with one square mesa on it, the smallest model that carries the plateau top #699 is about. The hills fixture next door mixes four surface characters on purpose, which makes it a good coverage benchmark and a poor unit test: nothing in it can be pointed at and called "the plateau". Here the plateau is a square of known size at a known Z, in 28 triangles, so a test can ask the one question that matters — does the tool centre ever travel *inside* it — and get an unambiguous answer. `topHalf` is the lever: a top clearing `PI * r^2` is reachable and must be machined, one under it is the area #682/#685 rule out and must still be left alone, and the same fixture therefore covers both sides of the rule
- `plasmaExportFixtures.ts` — plasma projects exported through the real plasma toolpath and post-processor (issue #959): `exportPlasma` and the `PLASMA_EXPORT_SCENARIOS` the unit test and the QtPlasmaC simulator corpus share.
- `projectFixtures.ts` — constructs authoritative format 3.0 projects from concise geometry-bearing test drafts, replaces strict feature sets, and resolves instance geometry for assertions. For machining setups (issue #944): `withBottomSetup` adds a Bottom setup and moves operations into it, and `withoutSetupFields` strips a project back to the shape a pre-setup file had, to exercise the migration
- `stepFixtures.ts` — generated AP214 STEP text for the #784 importer tests: boxes and cylinders as B-rep solids, a curves-only file, and mm / cm / m / inch / foot / undeclared units, so no third-party STEP file is checked in
- `rotaryDepthCompare.ts` — `compareRotaryDepth()`, the point-by-point rotary depth comparison #1155 rn-a uses: every point of every move against the deepest baseline cut through the same along position and angle, interpolated along the baseline's segments (rings, helices, along passes, plunges), then across along between the adjacent baseline passes (deepest layer at each); a point with neither must be in the air, so none is skipped. `rotaryDepthCompare.test.ts` pins the adjacent-pass rule
- `rotaryCutterGouge.ts` — the cutter-body sweep the #1155 gouge checks share (`deepestCutterGouge`, `cutterBody`): the tool's real body (a flat cylinder, or a ball's sphere plus its shank) is swept along every cut move of a rotary operation at no more than a quarter tool radius of tool-centre travel, interpolating along, A and tip radius the way the controller does, and its deepest point inside a caller-supplied solid is reported with the move it came from. The solid is a depth callback, so `rotaryNeighbours.test.ts` runs the Hex prism with its two end faces and `rotaryNeighbourPartialOverlap.test.ts` runs both the prism and the Turn cylinder through the identical sweep -- the along extent is part of the body, so a pass one radius past a neighbour's end face is visible
- `rotaryWallFootSweep.ts` — what a rotary operation leaves at a neighbour's wall foot (#1155 slice rn-d), measured with the cutter's own body: one radial material profile per degree of A (`blankProfile`, `cutterPosesByAngle`, `sweepProfile`), where a flat endmill removes everything above its tip over its footprint and a ball removes only the band its section covers (so it keeps its own fillet at a wall, and the section for a ball finish runs on the material an earlier rough left). `wallFootLeftover` reads the leftover beside the face off that profile -- the edge where no material above the operation's own cut level stands, and how far past the leave boundary it sits -- after `leftoverLevel` takes that level from the profile itself, because the sampler's conservative lift (#1045 slice F) means the theoretical surface radius is not what the cutter cuts. It asserts nothing and never reads the sampler, so `rotaryNeighbourPartialOverlap.test.ts` measures its rn-d numbers (0.08594 -> 0.00000 in on the flat finish) with the same code `scripts/issue-1155-rn-d-ledge-probe.ts` reports
- `cannedShapeFixture.ts` — the two test-only canned-shape generators slice A ships instead of a real shape (issue #1112): a closed plate with a hole (nesting rule + expansion) and an open polyline (open-line operation). Registered only by the tests that call `registerTestCannedShapes`, never imported by the app's generator barrel.

These helpers are for tests only. Production code must use the normal store creation paths or the project-format decoder.
- `pocketLeftover.ts` — geometric leftover measurement for the #550 pocket-finish defect: Clipper booleans at 1e6 counts per unit compute the morphological opening of the nominal region by the finish tool radius and subtract the swept envelope of the emitted cuts, so a reachable corner no round cutter can enter never counts as a defect. Test/diagnostic infrastructure; the CLI form is `scripts/issue-550-leftover-probe.ts`

- `rotaryChiralReference.ts` — #1103 slice ca-a's chiral, tapered bar and its independent swept cutter/material reference: the section scales and turns as it is extruded along the bar, so the material a cutter can reach at one pose depends on **both** the along position and A. `chiralSupport` is computed from the analytic section (the solid cutter body over its axial footprint, including a ball's shank), never from the sampler or the mesh the generator reads; `diagonalGouge` walks a commanded diagonal path at emitted fractions. Shared by `rotaryAroundPasses.test.ts` (the ring path) and `rotaryContinuous.test.ts` (ca-c's helix), so the two slices check the same reference and cannot drift.
- `rotaryOperationFixture.ts` — small closed asymmetric imported model inside an X/Y round bar, with an Around setup and chuck; shared rotary integration and parity input.
- `crossAxisPrograms.ts` — the programs issue #1156 is decided on, and the one renderer that posts them: own-drive grbl programs from a real rotary operation (around rough/finish in mm and inch, a square blank, a bar along Y running along it) plus a hand-built smoke program and three controls, each one condition away from the rule (a tool-change template naming the cross axis, an origin off the centreline, a manual-index Top setup). Three builders serve correction-round tests and are not in the golden: `crossAxisJitterProgram` (a cross coordinate that moves by less than one format unit, plus an origin-shifted control), `crossAxisArcProgram` (a real machine-plane circle at 5 mm, where the format half of condition 3 decides, and at 0.0004 mm, a quarter of the format grid, where four arcs are still fitted and the arc clause alone withholds the rule), and `machineWithToolChangeCommands` (extra tool-change text, for multi-line and compact-word scans). `crossAxisLetter` says which machine letter a program's cross coordinate is written under. Nothing here asserts; the rule's suite reads it, and `src/engine/gcode/crossAxisHeldPrograms.golden.json` is its frozen base-commit output.
- `rotaryBoltFixture.ts` — the canned Turn-plus-Hex bolt #1155 rn-b's cache tests share (`rotaryBoltFixture`, `translateAcrossBar`, `rotaryBoltOperation`): a Ø20 bar along X, a Ø4 Turn over along 10..50 and a 4 mm across-flats Hex over 10..20, built by `planRotarySolid`. The Turn is deliberately narrow and the tool Ø0.5, because on rn-a's own bolt (Ø10 Turn, Ø4 tool) the target's box grown by two tool diameters already covers the whole bar, so the across-the-bar hole the footprint fix closes cannot be observed there. The Hex can start centred or moved across the bar, and a second Turn can be added wholly outside the first one's along span
- `reportedRotaryMachines.ts` — the machine data and project shape of issue #1112 item 35, copied **verbatim** from the reporter's My Machines library (`mach3-copy`, "Mach3 (w/rotary)") and from the saved `.camj` (`grbl-1-1-copy`, "GRBL 1.1 (copy)"), plus `reportedRotaryProject()` which puts either one in an inch rotary project with the reported displayed operations. Both the export-path suite and the dialog-rendering suite read this one copy, so the data and the project shape cannot drift between them; it asserts nothing.
- `squareSimulationFixture.ts` — the accepted square-blank Around fixture (issue #1016 C2): an asymmetric imported prism on a square bar with the real default chuck and production `computeOperationToolpath`, plus the input/result-args builders the app-wiring suite uses, including the grid initialization descriptor.
