# INDEX — src/store/

Zustand store. The single source of truth for the current `.camj` project. **All project mutations must go through actions on `projectStore` — never mutate state directly.**

## Files
- `projectStore.ts` — store composition root: initial state, shared dependencies, and slice assembly
- `faceViewStore.ts` — workspace-local face state that is not part of the project (issue #945): whether the other side is drawn as a ghost, and the pending authoring-face change awaiting confirmation. Never dirties a file and is not an undo step
- `toolpathRendererStore.ts` — the sketch's GPU / Canvas renderer choice and status, published for the generation gear menu (issue #1102). View state only: never in the project file or undo history
- `workspaceFace.ts` — `switchWorkspaceFace`: the one place the UI changes the active setup. Refuses while an edit is in progress; a face the project has no setup for is looked at provisionally, without changing the project. `requestAuthoringFaceChange` opens the change-face confirmation under the same guard
- `faceBoundaries.test.ts` — where the two faces must not leak into each other: a ghost reached by feature id (driving dimensions, `moveFeatureControl`), a new shape judged against solids at its own face only, a provisional setup made real only by creating content (never by a restore), the face held while a shape is half drawn, text pasted across faces, a folder's eye, and the one ghost rule
- `workspaceFace.test.ts` — the face switch (looking at Bottom leaves the project untouched; the first Bottom feature, operation or setup edit makes the setup real in one undo step; undo/redo keep the face), the busy guard, linked copies shared across faces, the active face stamped on new features with a span measured from that face, Lines inside a Bottom pocket, Bottom text mirrored exactly once (both flip axes), ghosts that cannot be selected or hovered, paste and origin placement following the face
- `surfaceSlope.test.ts` — slope-setting normalization, save/open, clearing, undo/redo, malformed-input fail-closed behavior, and cache invalidation lifecycle
- `types.ts` — store-internal types (state shape, action signatures)

## Subfolders
- `slices/` — focused slices of store behavior
  - `selectionSlice.ts` — which features/segments are currently selected
  - `pendingActionsSlice.ts` — queue of deferred ops awaiting user confirmation
  - `pendingAddSlice.ts` — in-progress feature being drawn but not yet committed, including multi-step gear placement; re-arms a fresh draft of the same shape on completion (sticky drawing, issue #415). Arming a drawing tool, and every drawing completion in this slice, is refused on a square blank's Around sheet — round-only for hand-drawn geometry (#1016 C2-U1) — while clamp placement and the tab tool keep their own rules (`tab` refuses every Around face)
  - `pendingCompletionSlice.ts` — partially-completed sketches awaiting closure. Completing a pending offset, cut or join is also a square-blank Around creation boundary (#1016 C2-U1F): the derived rows keep their source's authoring face, so the completion judges that face (not the workspace face) and refuses atomically — before the join's `selectFeatures`/pending clear and before the offset's or cut's direct write — leaving project, selection, history and the pending request untouched. The same boundary covers the copy completions (#1016 C2-U1G): `completePendingMove` in copy mode (reference, independent and whole-grouped-folder copies) and `completePendingTransform` with `keepOriginals` (rotate and mirror) refuse an Around-copying request on a square blank before any write, while in-place move/rotate/mirror/resize and the clamp/tab/backdrop branches are unaffected
  - `featureDistributionSlice.ts` — transient one-shot grid/radial/path copy distribution; commits reference or independent instances as one undoable action (issue #205). A square blank's round-only Around sheet refuses the whole commit (#1016 C2-U1G) when a created copy would be Around-authored: the refusal is judged on the rows about to be created, not the workspace face, and returns before the source placement moves, the pending request clears, or any history or selection write; Top and STL distribution stays available
  - `nestingSlice.ts` — sheet nesting (issue #741): the Nest panel's `pendingNest` subject (`startNest`/`cancelNest`) and the `applyNest` / `discardNest` commits, each exactly one history entry; `applyNest` can replace an existing nest in the same step. `applyNest` computes the pure result and inspects the ACTUAL `copyIds` rows in the resulting project before committing (#1016 C2-U1G): any copy that would be Around-authored on a square blank — including a contained member collected by `resolveNestParts` but never selected — rejects the entire result, so no partial nest and no source placement change lands; move-only nests and Top/STL nests stay allowed
  - `textLayoutSlice.ts` — transient text-on-arc/path workflow: applies a baseline to an **already placed** text run (grouped with the distribution workflows, not with text creation), bakes a picked guide outline into it, and writes the baseline to the **instance row** (`FeatureInstance.textLayout`) rather than the shared definition, so curving one copy leaves its siblings straight (issue #671)
  - `dimensionsSlice.ts` — persistent dimension annotations (`project.annotations`): add/update/delete + selection (history-tracked)
  - `dimensionToolSlice.ts` — transient measure tools: tape measure + in-progress permanent-dimension placement (not persisted, not in history)
  - `featureSlice.ts` — feature CRUD, tree/folder management, primitive constructors including gear+bore grouping, arrange (align/distribute), and boolean ops (merge/cut/offset). `addFeature` refuses a feature that would be authored on the square blank's round-only Around sheet (#1016 C2-U1) before any id, asset, tree, history or selection work. `addFeature` and `reorderFeatures` keep the base-solid rewrite (the first solid becomes Add) except in a rotary project with bar stock, where the bar is the material (#1054). The direct derived paths — `offsetSelectedFeatures`, `mergeSelectedFeatures`, `cutSelectedFeatures` — insert without passing through `addFeature`, so each refuses the same way, judged by each derived row's own authoring face (the source's face, which survives a workspace move) rather than the workspace face (#1016 C2-U1F), while a generated Top model from C2-B never passes through either. `expandTextFeature` is the same kind of boundary (#1016 C2-U1G): its generated glyph rows copy the text row's authoring face, so an Around text run on a square blank is refused atomically before folders, definitions, rows, selection or history are written, while Top and round-bar Around expansion is unaffected
  - `featureGeometrySlice.ts` — feature sketch/profile geometry edits: moving controls, inserting/deleting/disconnecting points/segments, joining open endpoints, and corner fillets
  - `toolsSlice.ts` — tool CRUD: add/import/update/delete/duplicate tool definitions
  - `clampsSlice.ts` — clamp CRUD: add/update/delete/duplicate clamp, set visibility, move control point
  - `tabsSlice.ts` — tab CRUD: update/delete tab, set visibility, move control point, and manual auto-placement through the pure `engine/operations/autoTabs.ts` builder
  - `backdropSlice.ts` — backdrop CRUD: load/set/update/delete backdrop image
  - `machineDefsSlice.ts` — the project's machine snapshot: one `setProjectMachine` action that atomically embeds or clears the selected definition (history-tracked), plus the `machineSnapshot`/`projectWithMachine` helpers the New Project dialog shares through `projectWithProjectType`. Both the action and `projectWithMachine` write through `helpers/machineDefinitions.ts`: selecting a different machine rescues the old one instead of replacing the list, and a blocked library keeps it in the project (#1119). The snapshot is read structurally (#1119), so a machine whose templates still break a rule is embedded unchanged and export refuses it instead of the selection throwing or clearing. The machine *library* lives in [`src/machine/`](../machine/INDEX.md) as an application preference and never touches the project.
  - `operationsSlice.ts` — operation CRUD (a new or edited target the operation's machining setup cannot reach is refused, issue #946), rest-operation creation, toolpath visibility, duplication, ordering, and the single-history-transition `applyCamPlan` action
  - `setupsSlice.ts` — machining setups (issue #944): create/rename/update/delete setup, the active setup, move an operation to another setup (validated since #946: `planOperationMove` re-judges its targets from the new face, drops the unreachable ones and refuses a move that would leave none), set a feature's authoring face; plus `withSetupSync`, the `set` wrapper that reconciles setups after every project change and, in the same pass, keeps a round bar's chuck and tailstock centred with a derived height (#392 slice C). The wrapper uses syncWorkspaceSetups to keep a face being looked at provisional; withGhostSelectionGuard prevents ghost selection (#945)
  - `projectLifecycleSlice.ts` — project lifecycle and persistence actions: create/load/open/save, metadata display settings, and export path markers
  - `historySlice.ts` — undo/redo and history transaction lifecycle. The active machining setup is a view choice (issue #944): a snapshot is restored onto the setup the workspace is on, and a transaction that only switched setups leaves no undo step
  - `workpieceSlice.ts` — stock, stock-source sketch editing, grid/units, origin placement, and creation target actions. `setStockShape` is the one block/bar switch (#392 slice C, square blank #1016 C2-S2): the origin follows, a bar gains a chuck, a block loses every chuck and tailstock, all in one undo step; a written square blank is kept canonical (across width = side), and `setRectStockDimension` treats an across change as the side (and Z extent) and an along change as the length.
  - `importMergeSlice.ts` — shape import and `.camj` folder merge actions. An `importShapes` call on a square blank's Around sheet returns nothing before any folder, id, definition, history or selection work (#1016 C2-U1)
  - `constraintsSlice.ts` — persistent fixed-distance constraint placement, value updates, cancellation, and deletion
  - `treeVisibilitySlice.ts` — feature-tree visibility toggles for all regions/construction, folders, region/construction folders, and folder selection
- `helpers/` — pure helpers used by the store
  - `clipping.ts` — clipper-lib wrappers (handles the integer scaling factor): profile↔Clipper-path conversion, boolean/offset execution, and overlap predicates. Join connectivity counts area overlap or a positive-length shared boundary segment (issue #271); corner-only contact does not connect. Arc/curve reconstruction of Clipper output lives in `engine/toolpaths/arcReconstruction.ts`.
  - `derivedFeatures.ts` — computes derived snapshot features from the feature tree; also previewOffsetFeatures, joinOpenProfiles, and clearStaleConstraints
  - `featureDefinitions.ts` — definition/instance creation, orphan collection, operation propagation, and make-unique support for feature references
  - `featureMutations.ts` — authoritative definition/instance updates and folding resolved constraint translations back into lightweight rows. `applyFeaturePatch` keeps the base-solid rule (the first solid row becomes Add) except in a rotary project with bar stock, where the bar is already the material (#1054)
  - `gearFeature.ts` — grouped gear+bore feature insertion helper used by the gear creation action
  - `rotaryPatterns.ts` — canned Thread/Flutes on the Around face (issue #1016 C1 slice A): the pure sheet-line builder (start from the stock minimum along the bar, across from the centered `aroundFrame.zero`, `starts × pitch` lead, `C/n` start spacing, right-hand sign per bar axis, an optional `direction: 'left'` reversing the physical hand while keeping the lead magnitude and start spacing) and the one-undo-step store action that turns it into a named folder of ordinary open lines plus one Engrave operation (resolving or importing a V-bit for a thread). An existing V-bit or explicitly selected flute cutter stored in the other unit than the project is converted on a throwaway copy before it seeds the Engrave's feed/plunge/stepdown, so the operation lands in project units while the stored record, its id and the reference stay untouched (issue #1016 C1 slice A2). A thread's V-bit is chosen by its physical diameter — the raw `diameter` numbers are compared only after conversion to one common unit (slice A4) — so a 6 mm tool beats a 0.25 in (6.35 mm) one in either project unit, the saved records/order/ids are untouched, and the library still prefers an entry written in the project's units. No input parameters are persisted. Thread and Flutes are hand-drawn sheet geometry, so they stay round-bar authoring (#1016 C2-U1): a square blank is refused up front with the compatibility `needsRoundBar` detail even though the Around face itself is workflow-available there
  - `rotarySolids.ts` — ordinary generated solids on the Around face (issue #1016 C2-B): `planRotarySolid`/`addRotarySolid` for a polygon prism cut from a round bar and for the round finished target of a square-to-round job cut from a real square blank. One undo step creates a named features folder, one ordinary `model` feature holding the generated mesh (`serializeImportedMesh` → `normalizeImportedModelStorage` → `project.modelAssets`, `authoringFace: 'top'` so the persisted-model load pipeline accepts it, `z_bottom`/`z_top` equal to the emitted mesh's own bounds so the load fit is identity, and the mesh's absolute plan bounds as the closed sketch profile/silhouette) and one `rotary_rough` plus one `rotary_finish` operation targeting it in the active Around setup, with an existing flat/ball cutter seeded from a throwaway copy converted into project units (the stored record, id, units and values are untouched). The project/face/stock contract is checked explicitly — rotary project, matching bar shape, an active Around setup on the bar's axis — deliberately not through `aroundUnavailableReason`, which is the face's workflow guard; a provisional Around setup on a square blank is realised by the store's reconciler in the same write now that the face admits either bar (#1016 C2-U1, which removed the C2-B `provisionalAroundUnsupported` refusal). The target guards are used unchanged and no round stock is ever written. The input numbers are not persisted and a refusal changes nothing. The engine side (`buildRotaryPolygonPrism`, `buildRotaryCylinder`) builds absolute stock-space meshes with no stored parameter block
  - `featureRoles.ts` — single source of truth for feature roles (issue #199): isMachinable/isRegion/isConstruction/isSolid predicates, modelFeatures() CSG gate, and sectionForOperation tree sectioning. Use these instead of `operation !== 'region'` checks. `isSolid` (issue #270) returns true only for add/subtract/model — the base-solid invariant gate. `canChooseSubtract` predicts the store's base-solid rewrite and takes the project, because a rotary bar needs no base add (#1054)
  - `geometry.ts` — geometric utilities (bounds, transforms)
  - `transform.ts` — point/profile/clamp/tab translation, rotation, mirroring, and affine transforms; arc→bezier conversion
  - `shapeActionEligibility.ts` — shared join/cut selection eligibility (issue #522): `selectionQualifiesForImmediateJoin` decides whether a selection has already said enough to skip the join confirmation panel, `selectionQualifiesAsCutCutter` whether one selected feature is an unambiguous cutter. Every clause exists so the shortcut drops no member of the selection; anything failing falls back to the panel unchanged
  - `vcarveTargets.ts` — shared V-carve target eligibility predicate (issue #270 S2): `isVCarveCompatibleFeature` is the single source of truth for "can this feature be a V-carve machining target?"; used by UI hints, compatible selection, CAM panel validation, persisted target validation, and fallback target selection
  - `referenceTransforms.ts` — feature/backdrop resize, rotate, mirror from reference geometry; corner fillet radius and application
  - `modelAssets.ts` — imported model (STL) asset normalization, storage deduplication, and feature classification
  - `naming.ts` — unique-name generation for features, clamps, tabs, folders, and text features; text-feature creation
  - `operationDefaults.ts` — operation defaults: target validation, tool matching, kind labels, fallback targets, and default operation construction
  - `camPlanApply.ts` — stale-safe pure CAM-plan materialization: deduplicate/import tools, create rest regions and shared tabs, validate and append operations, and return one complete project for the store's atomic history transition
  - `copyFeatures.ts` — build rotated, mirrored, linear, and arbitrary-affine copies of features, clamps, and tabs; reference-vs-independent duplicate semantics with extractClonedDefinitions
  - `nestPart.ts` — sheet nesting, project side (issues #846, #855): selection → rigid parts (each touched grouped folder is one; the rest split by outline, overlapping outlines and a feature's own outlines kept together; contained features join; locked/model/cross-part-constraint refusals), gap from the outside edge routes' tools, obstacles (clamps + other features), sheet, and the serializable packer job with flattening and simplification tolerances
  - `nestApply.ts` — pure apply/discard of a nest: linked copies in a nest folder, copies joined to their sources' operations, intra-part constraint references re-pointed at sibling copies, originals moved or kept, and exact restoration on discard
  - `instanceTransforms.ts` — affine matrix builders and transform-delta composition for feature instances
  - `resolveFeatures.ts` — strict definition+instance resolver, ephemeral world-space read model, and commit boundary back to lightweight instances
  - `projectFormat.ts` — validates format 3.x projects, performs the one-way 1.0/2.0/2.1 legacy conversion without retaining baked rows, and migrates pre-3.1 absolute `retractHeight` values to distances above the material on load (issue #481) Plasma consumables backfill missing heights/delay without changing milling tools (issue #955). It also migrates files without machining setups — keyed on the missing fields, not the version — to a single Top setup (issue #944). A file without `meta.projectType` gets the one today's machine and stock imply (`inferProjectTypeFrom`, issue #1028); the format stays 3.3 and saving always writes the field. A loaded stock keeps its shape and axis — round through `normalizeRoundStock`, square through `normalizeSquareStock` (#1016 C2-S1, `thickness` = side) — while a `shape`-less, `'block'` or unknown value still becomes a keyless block, so old files serialize byte-identically. The legacy block-origin migration excludes every bar (#1016 C2-S2), so a square blank whose origin the user put on its min corner reloads unchanged
  - `profileEdit.ts` — pure profile and segment-editing helpers used by sketch editing and pending composite drafts
  - `buildShapeFeature.ts` — shared feature builder for the addRect/Circle/Ellipse/… constructors; consolidates duplicated shape-construction logic
  - `manualFeatureOperation.ts` — resolves existing world-space Add/Subtract instances and applies the shared strict-containment classifier to default a newly-created closed feature; on Around the bar is already solid, so a shape there always defaults to subtract (#395), and since #1054 the same holds on Top and Bottom of a rotary project, where the bar is the material on every face; a block keeps the base-solid classifier. Also `inferLineTopZFromEnclosingFeature` (issue #351) picks a newly-created Line's initial `z_top` from the smallest enclosing solid (subtract floor / add top)
  - `referenceFeatures.ts` / `referenceFeatures.test.ts` — resolved canonical candidates for explicit references (#994): same-face geometry plus opposite-face construction when its overlay is shown, leaving edit and CAM eligibility unchanged. Visibility is checked by each existing snap/hit consumer.
  - `activeFace.ts` — the workspace face (issue #945): the active setup and its face, `projectUsesBothFaces` (a Top-only project shows no face UI), the ghost predicate and `editableProjectFeatures` (what ordinary hit-testing, snapping and edits may see), `dropGhostSelection`, `newFeatureSpan` (a new feature's span measured from the face it is drawn on), `faceArtworkMirror`/`faceArtworkTransform` (the single mirror that makes Bottom text read correctly), the face-aware origin (`activeOriginInStock`, `originPlacementFromStock`), `flippedZRange` (a Bottom feature's Z as the stock sits flipped, so it reads like the same feature on Top), `faceAngles` (how a typed or displayed angle reads on the active face — headings, in-plane turns and rotations about a stock axis; each map is its own inverse and stored angles stay in stock space), `faceOffsets` (the same for a signed distance along a stock axis: a grid's spacing), `ghostPredicate` (the one ghost rule), `featuresAtActiveFace` (the solids a newly drawn shape is judged against), `crossFaceArtworkMirror` / `crossFaceArtworkTransform` (the mirror a text run gains or loses when pasted onto the other face), `isFaceEditInProgress` (the busy guard every face change obeys), `linkedCopiesOffFace` (how many linked copies of a shape sit on the other face), `isThroughFeature` and `resolveStockSpan`; `aroundUnavailableReason` says why the Around face cannot be entered — a non-rotary project first (`needsRotaryProject`, issue #1028), then a bar (`needsRoundBar`, the string kept for compatibility now that it means "not a bar at all"), and nothing else: machine capability and axis alignment are output-boundary concerns (issue #1034), so its result union carries only those two authoring reasons and no caller can branch on a machine condition, and the face-derived helpers treat Around as its own face with Top-style artwork, origin and depth; either bar shape is workflow-available (#1016 C2-U1), so `aroundSketchAuthoringAvailable` is the separate, narrower round-only **sheet** permission — a rotary project on a round bar — and `aroundSketchAuthoringRefused(project, face)` composes it with workflow availability, so a square blank's Around sheet refuses hand-drawn 2D authoring while a block is left to the availability guard
  - `provisionalSetup.ts` — looking at a face the project has no setup for (issue #945): the provisional setup ids, `provisionalSetupFor`, `realizeProvisionalSetup`, `syncWorkspaceSetups` (the store's reconciler: keeps a looked-at face provisional and makes its setup real when a write creates content there, never when it only restores a snapshot) and `keepWorkspaceFace` (undo/redo stay on the face in view). Around's provisional setup is built from either bar's axis — round or square (#1016 C2-U1) — not a fixed orientation, and a Bottom one follows the same bar axis in a rotary project so A180 turns the bar (#1054 slice 2). `project.setups` is never touched by looking
  - `setups.ts` — machining-setup bookkeeping (issue #944): `decodeSetups` (strict validation of the setups a file carries; an orientation or indexing mode this build cannot machine is an error, not a fallback, and an `'around'` setup is accepted only at angle 0 with manual indexing and only once per project), `syncProjectSetups` (the reconciler — at least one setup, a valid active setup, every operation in a setup, `operationIds` rebuilt from membership and project order, references to deleted features dropped, and an Around setup's axis kept on the bar's), a square blank repairing an empty Around setup's axis exactly as a round bar does (#1016 C2-U1), and `findSetupWithTurn`, which places an operation imported from another project on a setup turned the way its source was — comparing `kind` too, so Around never matches Top — with no fallback, so the importer adds that setup rather than move the operation to another face
  - `ids.ts` — ID generation/uniqueness
  - `projectType.ts` — the project type and the rules that read it (issue #1028): `inferProjectType` (what today's machine and stock imply, used once on load; either bar shape — round or square — infers rotary, #1016 C2-S1), `inferProjectTypeFrom` for the load migration's incomplete meta, `projectType` (the stored field, with the same inference as a fallback for a hand-built project), `machineMatchesProjectType` (plasma ↔ a plasma machine, rotary ↔ a router with a `rotary` block, milling ↔ any router) and `projectMachineMismatch`, `stockShapesForProjectType` (block for milling and plasma; rotary turns either bar, round first, #1016 C2-U1), `aroundFeaturesActive`, `barSeedsModel` (a rotary project on either bar: the stock is the part's material on every face, so no base add is needed, #1054), `manualIndexingApplies` (a rotary project on a bar: Top/Bottom programs state the manual A angle and a new Bottom setup flips about the bar, #1054 slice 2), `operationCutsUnderProjectType` and `operationCutsInProject` (the kind rule plus the setup's face — an Around setup's operations are not cut outside rotary, and on a rotary **square blank** a non-rotary operation there is kept and disabled so only the generated rotary models cut, #1016 C2-U1; the one predicate behind the export checklist and the CAM note).
  - `projectTypeApply.ts` — `projectWithProjectType` (issue #1028): sets the stored field, gives the stock the shape the type offers through `projectWithStockShape`, selects the first candidate machine that suits it, and moves the workspace off an Around setup a non-rotary type has no face for. Used by the New Project dialog — the only place a project is given a type since #1046; nothing is deleted and the same project object comes back when nothing changes. Selecting Rotary preserves an already-square blank (#1016 C2-S2); leaving Rotary converts it to a block through the existing path
  - `stockShape.ts` — block↔bar conversion, resizing a bar, and the origin that follows a stock edit (#392 slice B, square blank #1016 C2-S2). `toRoundStock`/`toSquareStock`/`toBlockStock` keep the box, the material, the colour, the visibility and the stock origin point; switching between the two bar shapes relabels the same box, so the axis, the centreline and the length are preserved even when the bar is shorter than it is wide. `resizeRoundStock`/`resizeSquareStock` keep the centreline and the start end and always return a canonical bar (a bad side/length/axis is refused with a `RangeError` before anything is built); `originAfterStockEdit` moves the machine origin only while it still sits on the stock's default; `projectWithStockShape` (slice C, extended by C2-S2) is the one shape switch — a bar (round or square) gains a chuck with its own default, switching between the bar shapes keeps the one already there, and a block loses every chuck and tailstock. `toBlockStock` narrows on "is a bar" (`isBarStock`) so a square blank counts as a bar.
  - `roundWorkholding.ts` — a bar's chuck and tailstock (#392 slice C, square blank #1016 C2-S2): `isRoundWorkholding`/`roundWorkholdingDiameter`, `defaultRoundWorkholding` (the size, place and height rule — a square blank's default diameter clears the corner envelope, `4 × barMaxRadius`), and `syncRoundWorkholding`, which recentres them and derives their height from the true pivot (`barPivotZ`) on every store write without ever enlarging a diameter the user set by hand, so the existing engine clamp check needs no bar case
  - `normalize.ts` — lower-level project normalization helpers: incompatible tool-reference repair, cloning, ID deduplication, cache clearing, equality checks, and feature tree/sync helpers. `normalizeMachineDefinitions` compacts an unselected machine only after a durable rescue; with no rescue seam the definitions stay in the project (#1119). `syncFeatureBasedStock` excludes every bar (`isBarStock`), so a round or square blank can never be re-derived from a feature (#1016 C2-S2). `isFirstFeatureValid` takes the project so a rotary bar's leading Subtract is valid (#1054)
  - `machineDefinitions.ts` — the one gate for every write of `meta.machineDefinitions` (#1119): `projectWithMachineDefinitions` rescues each definition a write would drop, and keeps it in the project when there is no seam or the rescue is not durable. An explicit user delete (clearing the selection), an unmodified bundled copy, and an explicitly authorized in-place update of the selected copy (the user accepting a newer version of that machine) are the only removals that do not need a rescue; any other same-ID collision keeps the existing content under a re-keyed id. Load/normalization paths use `normalizeMachineDefinitions` as their single rescue-or-keep gate instead
  - `polygonSplit.ts` — splits polygons (e.g. for boolean ops)

## Gotchas
- The store owns history — call actions, do not bypass them.
- Clipper math is integer-scaled; helpers in `clipping.ts` handle the factor. Don't roll your own.
